# Security

> Status: Phase 2 design. "Current" = audited behavior in Phase 1; "Planned" =
> hardening landing in Phases 4–6.

## Authentication

### Admin (current + hardening)

- Single admin account; credentials come from environment variables only — no
  hardcoded passwords in the repo.
  - `ADMIN_USERNAME` (default `admin`)
  - `ADMIN_PASSWORD_HASH` — bcrypt hash; login returns 503 if unset.
- Session: custom HMAC-SHA256 token in an HttpOnly, SameSite=Lax cookie
  (`quiz_admin_session`, 8h). No JWT library needed.
- **Planned hardening (Phase 4):**
  - Constant-time signature comparison (current string `!==` is timing-unsafe).
  - Refuse to boot in production when `SESSION_SECRET` is unset — remove the
    `'dev-secret-change-me-in-production'` fallback outside development.
  - Rotate/shorten session TTL; re-check the cookie on every admin socket event
    (already done) and every admin HTTP route (already done for `/api/admin/me`).

### Students (planned, Phase 5)

- No student passwords. A team authenticates by presenting a valid quiz code +
  known group name to `POST /api/join`; the server issues a team-scoped signed token.
- The team token identifies the socket; students can only act for their own team.
- Quiz codes are rotatable by the admin and are not sufficient alone once rotated.

## Authorization

| Surface | Rule |
|---|---|
| `/admin/*` pages | Edge `proxy.ts` cookie-presence gate + client fetch of `/api/admin/me` |
| `/api/admin/*` (except login) | Full HMAC verification server-side |
| Socket `admin:*` events | `socket.data.isAdmin` from handshake cookie — checked per event |
| Student events | Must hold a valid team token for the target room (planned) |
| Score/winner fields from clients | Never trusted; computed server-side |

Browser-side checks are UX only; all rules are enforced server-side.

## Transport & Headers

- Session cookie: `HttpOnly`, `SameSite=Lax`, `Secure` in production.
- **Known gap (Phase 6):** Socket.IO currently uses `cors: { origin: '*' }` with
  cookie auth (`withCredentials`). Planned: restrict `origin` to the deployed origin
  via env (`CORS_ORIGIN`) and reject credentialed handshakes from other origins.
- HTTPS termination is expected at the hosting platform in production.

## Secrets & Configuration

- `.env.example` lists placeholder names only; real values live in `.env.local`
  (gitignored) or the host's secret manager.
- Never commit actual secrets. The repo currently contains **no** working password.
- Admin bcrypt hashes are generated by the operator, not shipped in the repo.

## Input Validation

- Every API body/param and socket payload is parsed with Zod on the server
  (Phase 3+). Unknown fields are stripped; types and lengths are enforced.
- No reliance on HTML form or client JS validation.

## Rate Limiting & Abuse (planned, Phase 5–6)

- `POST /api/join` and `buzzer:press` are the main abuse surfaces — plan: per-IP and
  per-socket rate limits; repeated invalid join attempts back off exponentially.
- Admin credential brute force: login route will add per-IP delay after N failures.

## Data Sensitivity

- No personal student data beyond team names and member display names.
- No database; in-memory only. **State resets on restart** and is not durable —
  do not treat it as a system of record.
- Logs must not print session tokens, passwords, or full cookies.

## Operational Caveats

- Running without a database means there is no audit trail across restarts.
- Single-process architecture: do not run multiple replicas — in-memory state does
  not replicate between processes.
