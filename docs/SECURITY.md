# Security

> Status: audited production-boundary design. FastAPI and SQL Server are the runtime authority;
> the former Node/Socket.IO compatibility layer has been removed.

## Authentication

### Admin (current + hardening)

- Single admin account; credentials come from environment variables only — no
  hardcoded passwords in the repo.
  - `BACKEND_ADMIN_USERNAME` (default `admin` for local development)
  - `BACKEND_ADMIN_PASSWORD_HASH` — bcrypt hash; production startup fails closed if unset or
    malformed.
- Session: signed FastAPI token in an HttpOnly, SameSite cookie
  (`unknown_admin_session`). Production rejects default secrets and development bypasses.
- Production configuration also rejects the default admin username, auth secrets shorter than
  32 characters, wildcard CORS/trusted-host settings, and SQLite as the production database.

### Students

- No student passwords. A team authenticates by presenting a valid quiz code and team ID to
  `POST /api/v1/auth/team/join`; the server issues a session-scoped signed token.
- The team token identifies the participant; students can only act for their own team and session.
- Quiz codes are rotatable by the admin and are not sufficient alone once rotated.

## Authorization

| Surface | Rule |
|---|---|
| `/admin/*` pages | Edge `proxy.ts` cookie-presence gate + FastAPI auth check |
| `/api/v1/admin/*` | FastAPI admin dependency verifies the signed token |
| FastAPI WebSocket | Admin or session-scoped team token required |
| Student mutations | Session-scoped team token and database ownership checks |
| Score/winner fields from clients | Never trusted; computed server-side |

Browser-side checks are UX only; all rules are enforced server-side.

## Transport & Headers

- Session cookie: `HttpOnly`, `SameSite=Lax`, `Secure` in production.
- API responses include `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: no-referrer`, and a restrictive `Permissions-Policy`; production additionally
  sends one-year HSTS with subdomains.
- FastAPI uses an allowlisted `BACKEND_CORS_ORIGINS` configuration with credentialed cookies.
- Unsafe requests carrying cookies are additionally rejected when their `Origin` is outside that
  allowlist.
- The browser quiz transport is native FastAPI WebSocket; no Socket.IO compatibility server is
  shipped in the application runtime.
- HTTPS termination is expected at the hosting platform in production.

## Secrets & Configuration

- `.env.example` lists placeholder names only; real values live in `.env.local`
  (gitignored) or the host's secret manager.
- Never commit actual secrets. The repo currently contains **no** working password.
- Admin bcrypt hashes are generated by the operator, not shipped in the repo.
- CI audits the production JavaScript dependency graph at moderate severity or higher; development
  tooling is excluded from the production dependency graph.
- `backend/scripts/generate_password_hash.py` prompts without exposing the plaintext password in
  process arguments or application logs; the resulting hash is injected through the secret manager.
- Bcrypt-hash rotation affects new logins. Auth-secret rotation is required to invalidate already
  issued signed tokens.

## Input Validation

- Every FastAPI body and parameter is parsed with Pydantic; types, lengths, enum values, and
  cross-field invariants are enforced before service logic runs.
- No reliance on HTML form or client JS validation.

## Rate Limiting & Abuse

- `POST /api/v1/auth/login`, team join, buzzer, and answer endpoints have bounded sliding-window
  limits. Buzzer and answer limits include the authenticated team identity.
- Rate-limit events and per-bucket coordination rows are stored in SQL Server, so all API workers
  observe the same window. The bucket row is locked while the window is evaluated.
- Password hashes are generated by the operator and injected as `BACKEND_ADMIN_PASSWORD_HASH` by
  the backend secret manager.
- **Stateless logout:** tokens are HMAC-signed without a server-side revocation list; logout
  clears the cookie but an already-issued token stays cryptographically valid until expiry (8h).

## Data Sensitivity

- No personal student data beyond team names and member display names.
- SQL Server is the system of record for quiz sessions, questions, participants, answers, scores,
  and audit history. Backups must be encrypted and restore-tested.
- Logs must not print session tokens, passwords, or full cookies.
- WebSocket authentication uses a subprotocol rather than a query-string token, preventing signed
  team tokens from appearing in URL/access-log records.

## Operational Caveats

- Production must run against SQL Server; the shared rate-limit tables and locking migration must
  be applied before multiple API workers are deployed.
- Production scheduling, secret-manager injection, monitoring, and restore evidence remain release
  owner responsibilities.
